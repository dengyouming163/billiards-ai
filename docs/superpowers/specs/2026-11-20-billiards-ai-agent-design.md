## 1. 背景与目标

球房系统已经稳定运行三年，具备真实门店、角色、订单、支付、会员、库存、交班、设备和前端业务闭环。项目目标不是重新制作通用 Agent 演示，而是在完整生产业务副本上增加三个相互关联的 Agent 场景：

1. 交班对账只读 Agent；
2. 开台协同受控执行 Agent；
3. 经营值班主动 Agent。

项目同时承担两类验收：

- **生产验收**：减少人工核查和重复操作，结果可追溯，失败可恢复，Agent 故障不影响原有手工业务。
- **面试验收**：形成 Agent 编排、工具调用、RAG 协作、AI 全栈交互、权限、安全、可靠性、评测和生产灰度的真实证据。

仅有架构梳理不能视为 Agent 项目完成。M1 完成后可开始正式投递；M2 完成后可将本项目作为 Agent + AI 全栈岗位的简历主项目；M3 用于增强主动任务和生产深度。

## 2. 核心原则

1. 球房业务系统负责业务正确性，Agent 负责理解、规划和协调，RAG 负责制度与 SOP 知识。
2. 财务计算和经营汇总使用 SQL 与确定性规则，大模型不得口算账务或虚构实时数据。
3. 写操作必须通过球房业务 API 和原有业务规则，不允许 Agent 直接修改订单、台位、支付、库存或设备表。
4. RAG 检索结果只作为制度证据，不能作为实时经营事实。
5. 三个场景共用 Agent 内核、身份、工具治理、运行记录、审计和评测，不建设三个独立 Demo。
6. 不为覆盖名词提前引入多 Agent、MCP、Kubernetes 或通用 Agent 平台。
7. 所有简历指标必须来自真实测试、评测或生产统计；没有测量就不宣称提升比例。

## 4. 总体架构

```text
wwwstore 管理端 / wwwpos 收银端
              ↓ HTTP + SSE
       FastAPI Agent API
              ↓
       LangGraph 状态图
       ├── 交班对账图
       ├── 开台协同图
       └── 经营值班图
              ↓
          统一工具层
       ├── RAG Search API
       ├── 球房只读查询工具
       ├── 球房业务命令 API
       └── 定时器与业务事件
              ↓
身份 / 权限 / 参数校验 / 审批 / 幂等 / 审计 / Trace / 评测
```

### 4.1 Agent 服务

使用 Python、FastAPI、Pydantic 和 LangGraph。模型适配器支持 OpenAI 兼容的工具调用、结构化输出、用量统计、超时和有限重试。现有 RAG 的纯文本 `ChatClient` 不直接承担 Agent 工具调用。

Agent 使用独立 PostgreSQL 数据库保存运行、步骤、checkpoint、审批、工具调用和审计记录。LangGraph 使用持久化 checkpointer，等待人工确认的任务可以跨进程恢复。

后台任务使用数据库任务表和 `FOR UPDATE SKIP LOCKED` 领取，第一版不引入 Redis。只有出现经测量的队列需求时才重新评估独立消息基础设施。

### 4.2 RAG 接入

Agent 任务使用 `POST /v1/kbs/{kb_id}/search` 获取带 `chunk_id`、正文和元数据的制度证据，避免嵌套调用完整 RAG 问答造成重复生成。

纯制度问答可以路由到现有 `/v1/chat/stream`。需要同时查询业务事实和制度知识时，由 Agent 分别调用业务工具与 Search 工具后统一组织结果。

RAG 的租户、知识库、ACL、RLS、拒答、引用和注入防护保持有效。Agent 不直接访问向量表。生产接入时，RAG 仅接受受信内网服务调用，不能将当前请求头占位身份机制直接暴露给不可信客户端。

### 4.3 球房业务接入

只读场景优先调用明确的业务查询接口；历史回放和复杂聚合可以使用严格只读的数据副本。写场景通过复制后的 ThinkPHP 业务代码提供清晰、受权限保护的命令 API，并复用原有开台事务和硬件联动。

门店、用户、角色和权限来自已验证的球房登录态，由服务端映射到 Agent 与 RAG 身份。前端或模型提交的门店、租户、用户和角色不能作为授权依据。

### 4.4 前端

- `wwwstore` 增加对账报告、证据下钻、经营值班、运行记录、审批与 Trace 页面。
- `wwwpos` 增加开台对话、参数补齐、开台预览、人工确认和真实结果展示。
- SSE 传输任务状态和文本增量；审批、取消和恢复使用明确 API，不通过普通聊天文本隐式执行高风险动作。

## 5. 三个场景的数据流

### 5.1 交班对账只读 Agent

```text
确定门店和班次
→ 查询交班汇总
→ 分解订单、支付、充值及代码中实际存在的相关流水
→ 使用确定性规则计算和分类差异
→ 必要时检索交班处理 SOP
→ 输出一致项、疑似差异、原始证据和不确定项
→ 支持基于同一任务状态继续追问
```

对账口径以现有球房 Schema 和业务代码为准，不预设代码中不存在的财务概念。系统能够证明的差异与需要人工实际金额或外部账单才能判断的差异必须分开标记。

### 5.2 开台协同 Agent

```text
接收自然语言请求
→ 校验用户和门店权限
→ 补齐会员、台型、台位和开台模式等必要参数
→ 查询实时空闲台位与适用规则
→ 生成开台预览
→ checkpoint 并等待收银员明确确认
→ 携带幂等键调用球房开台业务 API
→ 查询并返回真实订单结果
```

参数不足时必须澄清，不能猜测。台位被抢占时返回最新可选项。写接口超时后先查询真实结果，不得盲目重试。用户取消后不得执行命令。

### 5.3 经营值班主动 Agent

交班完成通过球房业务库中的事务性 outbox 事件传递；定时巡检由调度器生成任务。事件和定时任务均以唯一键去重，worker 原子领取并持久化进度。

Agent 发现异常后继续调用只读工具追查原因，结合 RAG SOP 给出处理建议，生成待办草稿。待办分派需要人工确认。通知复用现有管理端和 WebSocket 能力，并记录送达、查看和处置状态。

第一版保持单 Agent、多工具和明确状态图。只有任务确实需要并行、独立权限或独立上下文时，才拆分为多个专家 Agent。

## 6. 安全、可靠性与降级

- 工具分为只读、敏感只读和写操作，分别授权和审计。
- 所有工具输入使用 Schema 校验，输出使用结构化结果和统一错误类型。
- 只读工具可进行有限指数退避重试；非幂等写操作禁止自动重放。
- 开台命令必须包含权限预检、业务预检、人工审批和幂等键。
- RAG 文档、会员备注、交班备注和工具结果均视为不可信数据，不得改变系统指令或提升权限。
- 日志和 Trace 对手机号、证件、支付信息、密钥等敏感字段脱敏。
- Agent 不可用时，原有手工对账和开台流程继续可用。
- 灰度顺序为：本地测试、历史回放、测试门店、生产影子运行、生产只读、评估后的受控写入。
- 自动支付、退款、记账和直接设备控制不属于本项目的 Agent 自主权限范围。

## 7. 测试与评测

### 7.1 软件测试

- 模型响应解析、工具参数、权限、幂等和状态迁移的单元测试；
- Agent 与 RAG、ThinkPHP API 的契约测试；
- checkpoint 中断、恢复、取消和超时测试；
- 管理端和 Electron 的关键端到端测试；
- 原球房开台和交班业务回归测试；
- 重复提交、并发开台、模型异常、RAG 异常、数据库异常等故障注入。

### 7.2 Agent 评测

评测数据来自脱敏历史班次和测试门店，覆盖正常、差异、权限不足、缺数据及主要业务异常类别，并报告样本量与分布。

- 对账：数值准确率、差异识别率、误报率、证据可追溯率、工具选择准确率。
- 开台：任务成功率、参数正确率、重复执行率、越权拦截率、超时恢复正确率。
- 值班：异常准确率、可行动率、无效提醒率、任务重复率。
- 通用：P95 延迟、Token 与成本、人工确认率、人工修改率和失败类型分布。

评测记录模型、提示词、工具、知识库和业务代码版本，支持变更前后回归比较。Mock 结果只用于软件测试，不得作为生产收益证据。

## 8. 分阶段推进与验收

### M0：迁移基线与 Agent 最小内核

交付：完整脱敏源码副本、开发与测试环境、关键业务基线、FastAPI Agent 服务、工具调用模型适配器、RAG Search 工具、身份权限、运行与审计模型、管理端 Agent 页面和 SSE 基础协议。

验收：关键原业务行为可重复验证；RAG 与球房测试工具可调用；未授权身份被阻断；运行与工具 Trace 可查询。

面试状态：可介绍架构，但不作为已完成 Agent 项目。

### M1：交班对账只读 Agent

交付：完整对账状态图、只读业务工具、确定性对账规则、SOP 证据、管理端报告与下钻、历史黄金集、评测与异常测试、业务耗时基线。

验收：黄金集中的确定性汇总与差异结果全部符合预期，所有数值均可追溯到查询和规则；证据引用覆盖率为 100%；越权请求全部阻断；无数据时明确标记为不可判断，报告可由人工复核。

面试状态：可开始正式投递，简历如实描述已完成只读对账场景。

### M2：开台协同 Agent

交付：开台状态图、参数补齐、实时台位工具、预览与确认卡片、checkpoint、审批恢复、幂等命令、冲突与超时处理、Electron 端到端测试。

验收：重复提交不会重复开台；并发抢占有明确结果；取消不执行；超时能够核对真实状态；未授权请求被阻断；原手工开台回归通过。

面试状态：可作为 Agent + AI 全栈岗位的简历主项目重点投递。

### M3：经营值班主动 Agent

交付：outbox、调度器、后台 worker、任务去重与恢复、异常追查、SOP 建议、待办草稿、通知和处置记录。

验收：重复事件不重复执行；worker 重启可恢复；异常提醒有证据；无效提醒可度量；人工不确认时不分派任务。

面试状态：具备主动 Agent、异步任务和生产运行深度，可支撑更高级的架构与可靠性问题。

## 10. 非目标

- 不通过堆叠框架代替业务闭环；
- 不开展模型训练、微调或推理优化；
- 不允许 Agent 自主支付、退款、记账或直接控制设备；
- 不用 Mock 数据冒充生产收益；
- 不等待三个场景全部完成才开始面试；
- 不因本项目忽略 Python、前端、计算机基础和通用面试准备。
